## 문제: 응답 하나에 추론 전체가 걸려 있었다

met·a·round의 AI 서버는 처음에 분석 요청을 동기로 처리했습니다. 요청을 받으면 추론이 끝날 때까지 응답을 보내지 않는 구조입니다.

추론에는 시간이 걸립니다. 서버 로그에는 추론마다 소요 시간이 기록되는데, 2026년 7월의 로그에서 실제 모델을 쓴 분석 요청은 수십 초에서 100초 이상까지 걸린 것으로 남아 있습니다. 호출하는 쪽은 그동안 연결을 붙잡고 있어야 합니다. 연결이 끊기면 응답으로는 결과를 받지 못하고 방을 따로 조회해야 합니다. 설계 문서에 타임아웃 사고가 기록된 것은 아니며, 전환의 근거는 추론 시간 자체입니다.

이 글은 **2026년 7월 22일의 설계 문서와 구현 계획**, 현재 저장소의 코드, 같은 날의 서버 로그를 바탕으로 정리했습니다. 제가 맡은 것은 AI 서버 쪽입니다. 결과를 수신하는 Spring 백엔드는 팀의 다른 구성원이 맡은 상대 시스템이며, 이 글에서는 AI 서버가 그쪽에 무엇을 보내는지만 다룹니다.

## 조건

- GPU 모델이 서버 프로세스에 상주합니다. 추론을 다른 프로세스로 옮기면 모델이 두 벌 올라가는데, 8GB GPU에서는 감당하기 어렵습니다.
- 저장소에 Redis 기반 작업 큐 코드가 있지만 연결되어 있지 않고, 큐를 소비하는 워커도 없습니다.
- 상대 시스템은 정해진 형식의 webhook 요청을 받는 것을 전제로 합니다.
- 분석 요청과 확정 요청 둘 다 대상입니다. 방 조회와 수정본 저장은 동기로 남깁니다.

## 가설: 접수와 결과를 분리하고, 상태를 복구 경로로 둔다

요청은 즉시 접수만 하고, 추론은 같은 프로세스의 백그라운드 작업으로 실행하며, 결과는 webhook으로 알립니다. 별도 워커 프로세스는 메모리 조건 때문에 채택하지 않았습니다.

webhook은 통지일 뿐이라는 점을 원칙으로 삼았습니다. 추론 결과에 따른 방의 상태는 통지 전에 이미 데이터베이스에 저장되어 있어야 합니다. 통지가 전달되지 않더라도 호출하는 쪽이 방을 조회해 상태를 확인할 수 있게 하기 위해서입니다.

## 방법 1: 접수

분석 요청을 받으면 다음 순서로 처리합니다.

1. 통지 주소를 정한다. 요청에 주소가 있으면 그것을 쓰고, 없으면 환경 설정의 기본 주소를 쓴다.
2. 방을 `analyzing` 상태로 먼저 저장한다. 결과가 없는 껍데기지만, 이 시점부터 조회가 가능하다.
3. 백그라운드 작업을 등록한다.
4. 방 ID와 접수 상태를 담아 202로 응답한다.

확정 요청도 같은 구조입니다. 방의 상태를 `reconstructing`으로 바꾸는 과정에서 방이 없으면 404를 동기로 돌려줍니다. 접수 전에 확인할 수 있는 오류는 webhook으로 미루지 않습니다.

## 방법 2: 백그라운드 작업

백그라운드 작업은 요청을 처리하던 데이터베이스 세션을 물려받지 않고 자기 세션을 새로 엽니다. 응답이 나간 뒤에는 요청의 세션이 이미 닫혀 있기 때문입니다.

작업의 구조는 단순합니다.

```text
추론 실행
 ├─ 성공: 결과로 통지 내용 구성
 └─ 예외: 방을 failed로 저장하고 실패 통지 내용 구성
항상: 통지 전송
```

추론과 상태 저장에서 난 예외는 작업 밖으로 올리지 않습니다. 전송 단계는 HTTP 계열 오류만 잡으므로 그 밖의 예외까지 막는 것은 아닙니다. 방을 실패 상태로 저장하는 일 자체가 실패하더라도 그 예외를 기록만 하고 실패 통지는 보냅니다.

## 방법 3: 통지 계약

AI 서버가 보내는 내용은 다음과 같습니다.

```json
{
  "aiRoomId": "<분석 요청에서 받은 방 ID>",
  "status": "WAITING_FOR_CORRECTION | SUCCESS | FAILED",
  "roomDataJson": "<JSON 문자열> | null",
  "modelUrl": null,
  "fileSizeMb": null,
  "format": null
}
```

| 상황      | `status`                 | `roomDataJson`의 내용         |
| --------- | ------------------------ | ----------------------------- |
| 분석 완료 | `WAITING_FOR_CORRECTION` | `aiVertices`, `aiEdges`       |
| 확정 완료 | `SUCCESS`                | `finalVertices`, `finalEdges` |
| 실패      | `FAILED`                 | `null`                        |

`roomDataJson`은 객체가 아니라 JSON 문자열입니다. 상대 시스템의 계약에 맞춘 것으로, 받는 쪽에서 한 번 더 해석해야 합니다. 내부 상태와 통지 상태의 대응은 한 모듈에서만 정의합니다.

전송은 최대 세 번 시도하고, 시도 사이의 대기 시간을 두 배씩 늘립니다. 세 번 모두 실패하면 오류를 기록하고 넘어갑니다. 통지 실패가 서버의 다른 요청에 영향을 주지 않게 하기 위해서입니다.

## 관찰 1: 설계와 구현이 달라진 지점

설계 문서와 현재 코드를 비교하면 두 곳이 다릅니다.

**통지 주소의 보관.** 설계는 분석 때 정한 주소를 방과 함께 데이터베이스에 저장해, 본문이 없는 확정 요청이 그 주소를 다시 쓰도록 했습니다. 현재 구현은 주소를 저장하지 않습니다. 분석은 정한 주소를 백그라운드 작업에 직접 넘기고, 확정은 환경 설정의 주소만 사용합니다.

**재시도 간격.** 설계는 1초·2초·4초의 대기를 적고 있습니다. 구현은 마지막 시도 뒤에는 기다리지 않으므로 실제 대기는 1초와 2초 두 번입니다.

## 관찰 2: 로그에 남은 동작

7월 22일의 서버 로그에서 다음을 확인할 수 있습니다.

- 분석 요청에 202가 응답된 뒤 `WAITING_FOR_CORRECTION` 통지가, 확정 요청 뒤에 `SUCCESS` 통지가 전송 성공으로 기록되어 있습니다. 로컬 수신 주소와 외부 주소 양쪽에 대한 기록이 있습니다.
- 가짜 모델을 쓴 한 실행에서는 분석 통지가 요청에 담긴 로컬 주소로 전달되었지만, 이어진 확정 통지는 환경 설정의 주소로 나갔고 그 주소가 404를 반환했습니다. 약 1초, 약 2초 간격으로 세 번 시도한 뒤 포기한 것으로 기록되어 있습니다. 위에서 말한 주소 보관의 차이가 그대로 드러난 사례입니다.
- 분석 중 예외가 발생하고 실패 상태 저장까지 실패한 실행에서도 `FAILED` 통지는 전송된 것으로 기록되어 있습니다.

단위 테스트는 가짜 저장소와 가짜 전송 계층으로 작성되어 있습니다. 성공 시 통지 내용, 실패 시 방의 상태와 통지, 서버 오류가 두 번 이어진 뒤 세 번째에 성공하는 경우, 끝까지 실패해도 예외가 올라오지 않는 경우를 기댓값으로 둡니다.

로그의 기록은 개발 중 수동으로 실행한 흔적입니다. 통지 성공률이나 지연 시간을 측정한 자료는 아닙니다.

## 한계

- 작업이 서버 프로세스의 메모리 안에서만 존재합니다. 추론 중 서버가 재시작되면 작업이 사라지고 방은 `analyzing` 상태로 남습니다. 이를 감지하거나 복구하는 코드는 없습니다.
- 동시에 여러 요청이 들어올 때 추론을 줄 세우거나 개수를 제한하는 장치가 없습니다. GPU 메모리 조건을 생각하면 보완이 필요한 부분입니다.
- 통지가 세 번 모두 실패하면 다시 보내지 않습니다. 호출하는 쪽이 방을 조회해 상태를 확인하는 것이 유일한 복구 경로입니다.
- 확정 통지는 환경 설정의 주소로만 갑니다. 분석 요청에 다른 주소를 지정했더라도 확정 결과는 그곳으로 가지 않습니다.
- 통지 요청에는 서명이나 인증 정보가 없습니다. 받는 쪽은 이 요청이 실제 AI 서버에서 왔는지 확인할 수 없습니다.
- 코드의 기본 통지 주소는 개발용 임시 터널 주소입니다. 배포 환경에서는 반드시 설정으로 덮어써야 한다고 문서에 적혀 있습니다.
