## 문제: 하나의 코너, 여러 개의 표현

met·a·round의 AI 서버에서 방의 코너 하나는 여러 모습으로 존재합니다. 모델이 추론한 3D 점이 있고, 그 점을 각 사진에 투영한 2D 점이 있으며, 사용자가 화면에서 고친 2D 점이 있고, 마지막으로 확정된 3D 점이 있습니다.

이 표현들이 섞이면 문제가 생깁니다. 사용자가 고친 점이 AI의 원래 결과를 덮어쓰면 비교할 수 없게 되고, 2D 점이 어느 3D 점에서 왔는지 잃어버리면 수정본을 3D로 되돌릴 수 없습니다. 엣지는 정점을 가리키기만 하므로, 정점의 구분이 흐려지면 엣지도 함께 흐려집니다.

이 글은 **2026년 7월 3일의 설계 문서**, 엣지 저장 흐름을 정리한 문서, 현재 저장소의 스키마와 저장 코드를 바탕으로 AI 서버 쪽의 데이터 계약을 정리했습니다. 백엔드와 클라이언트는 팀의 다른 구성원이 맡은 영역이며, 여기서는 이 계약을 주고받는 상대 시스템으로만 다룹니다.

## 조건: 세 가지 출처와 두 가지 좌표계

정점과 엣지는 출처(source)에 따라 세 종류로 나뉩니다.

| 출처        | 만들어지는 시점                                   | 좌표                    | `image_index` | `source_vertex_id`           |
| ----------- | ------------------------------------------------- | ----------------------- | ------------- | ---------------------------- |
| `ai`        | 분석 단계에서 3D를 2D로 투영                      | 원본 이미지 픽셀, z는 0 | 있음          | 원본 3D 정점의 ID            |
| `corrected` | 사용자가 수정본을 저장                            | 원본 이미지 픽셀        | 있음          | 옮긴 점은 유지, 새 점은 없음 |
| `final`     | 분석 단계의 3D 결과, 이후 확정 단계에서 다시 작성 | 3D                      | 없음          | 없음                         |

조건이 하나 더 있습니다. 사용자의 수정본은 AI가 만든 2D 정점의 ID를 그대로 다시 사용합니다. 같은 ID의 정점이 `ai`와 `corrected`에 동시에 존재하게 됩니다.

## 가설: 좌표는 정점에만, 동일성은 참조로

계약의 원칙을 세 가지로 잡았습니다.

- 엣지는 좌표를 갖지 않는다. 두 정점의 ID만 가진다.
- 2D 점과 3D 점의 연결은 `source_vertex_id` 하나로 표현한다.
- 같은 ID가 여러 출처에 있을 수 있으므로, 저장할 때는 ID와 출처를 함께 식별자로 쓴다.

## 방법 1: 모델과 서버 사이의 계약

3D 추론 전략은 종류와 관계없이 같은 형식의 결과를 돌려줍니다.

```python
{
  "vertices": [{"id", "x", "y", "z"}],          # 공통 좌표계의 3D 정점
  "edges":    [{"start", "end"}],                # 정점 ID 쌍
  "views":    [{"image_index", "vertex_id", "x", "y"}],  # 뷰별 투영
  "meta":     {...}                              # 카메라, 평면, 수직축
}
```

3D 정점·엣지를 서버의 객체로 바꾸는 일은 매퍼 한 곳에서 하고, 뷰별 투영(`views`)을 2D 정점으로 바꾸는 일은 파사드가 맡습니다. 모델 내부가 바뀌어도 이 형식만 지키면 그 뒤의 코드는 영향을 받지 않도록 하기 위한 경계입니다.

## 방법 2: 투영점은 새 ID를 받는다

3D 정점 하나는 여러 사진에 투영될 수 있습니다. 투영점이 3D 정점의 ID를 그대로 쓰면 같은 ID가 뷰 수만큼 생기므로, 투영점마다 새 ID를 발급하고 `source_vertex_id`에 원본 3D 정점의 ID를 적습니다.

3D 엣지는 양 끝 정점이 같은 뷰에 함께 투영된 경우에만 그 뷰의 2D 엣지로 내려갑니다. 내려간 엣지는 그 뷰 투영점의 ID로 연결됩니다.

## 방법 3: 수정본이 지켜야 할 것

수정본의 정점은 `image_index`와 `source_vertex_id`를 함께 보내야 합니다. 앞의 값은 어느 카메라로 3D에 올릴지를 정하고, 뒤의 값은 점의 종류를 정합니다. 옮긴 점은 원래 값을 유지하고, 새로 찍은 점은 비워 둡니다.

수정본은 변경분이 아니라 사용자가 남긴 전체 점 집합입니다. 어떤 3D 정점을 가리키는 2D 점이 모든 뷰에서 빠져 있으면 삭제로 해석합니다.

수정본이 있으면 확정 단계에서 `final` 엣지는 수정본의 엣지로 전부 다시 구성됩니다. 2D 정점 ID를 3D 정점 ID로 바꾸고, 양 끝이 같은 3D 점이 된 엣지와 중복 엣지를 제거합니다. 사용자의 선 편집을 우선하고 AI의 3D 엣지는 이때 버려집니다. 다만 뒤따르는 바닥 확장 보정이 발동하면 바닥 윤곽 엣지는 다시 생성됩니다.

## 방법 4: 세 출처를 함께 저장하기

저장소에서는 정점과 엣지 각각 한 테이블에 세 출처를 함께 둡니다.

- 정점의 기본 키는 `(id, source)`입니다. 수정본이 AI 정점의 ID를 다시 쓰기 때문에 ID만으로는 충돌합니다.
- 엣지의 기본 키도 `(id, source)`이고, 정점을 가리키는 외래 키 역시 `(정점 ID, source)`의 복합 키입니다. 엣지의 출처는 양 끝 정점의 출처와 같아야 합니다.
- 저장 순서는 정점 다음에 엣지입니다. 갱신할 때는 기존 정점과 엣지를 지우고 다시 넣습니다.

외부로 내보낼 때는 필드 이름을 camelCase로 바꿉니다. 분석이 끝나면 `ai` 정점과 엣지를, 확정이 끝나면 `final` 정점과 엣지를 상대 시스템에 전달합니다.

## 관찰: 계약의 빈틈이 드러난 지점

**보존 여부에 대한 테스트.** 수정본을 저장할 때 `image_index`와 `source_vertex_id`가 유지되는지, 저장과 복원을 거쳐도 `source_vertex_id`와 메타가 남는지를 확인하는 단위 테스트가 작성되어 있습니다. 첫 설계 문서에는 당시 수정본 저장이 `image_index`를 버리고 있어 고쳐야 한다는 기록이 있고, 이 테스트는 그 수정에 대응합니다.

**같은 뷰 조건이 만든 손실.** 3D 엣지를 2D로 내릴 때의 "양 끝이 같은 뷰에 있어야 한다"는 규칙은, 코너가 검출 뷰 한 곳에만 투영되던 것과 겹쳐 엣지 손실을 만든 것으로 7월 17일에 진단되었습니다. room4 사례에서 3D 엣지 16개 중 9개만 2D로 내려갔습니다. 이 사례는 [앞선 글](../metaroom-fragmentation/)에서 따로 다뤘습니다. 계약 자체는 일관되었지만, 계약이 표현할 수 없는 정보가 있었던 경우입니다.

**"수정됨" 표시의 의미.** 수정본이 한 번이라도 저장되면 방은 수정된 것으로 표시되고, 확정 단계는 AI의 3D 결과 대신 수정본을 3D로 올리는 경로를 탑니다. 진단 문서에는 클라이언트가 편집 여부와 관계없이 수정본을 먼저 저장해, 손대지 않은 방도 이 경로로 들어갔다는 기록이 있습니다. 문서는 클라이언트 쪽에서 편집이 없으면 저장을 생략하도록 완화했다고 적고 있습니다.

**남아 있는 불일치.** 요청 스키마의 주석에는 상대 시스템이 이미지 주소 하나를 보내는 데 비해 AI 서버는 경로 목록을 받는다는 차이가 잔여 불일치로 적혀 있습니다.

## 한계

- `source_vertex_id`에는 외래 키 제약이 없습니다. `final`이 다시 작성될 때의 부담을 피하려는 선택이지만, 가리키는 3D 정점이 삭제되어도 데이터베이스가 막아 주지 않습니다.
- `final`은 확정 단계에서 덮어쓰입니다. 분석 단계의 원본 3D 결과를 따로 보존하는 출처가 없어, 확정 이후에는 원본과 비교할 수 없습니다.
- 수정본은 전체 집합이어야 하므로, 일부만 보내면 나머지가 삭제로 해석됩니다. 이 규칙은 스키마로 강제되지 않고 약속으로만 존재합니다.
- 2D 엣지는 한 뷰 안의 점끼리만 이을 수 있습니다. 뷰를 넘는 엣지를 표현하는 방법은 미착수 항목입니다.
- 수정본의 검증은 기본적인 수준에 머뭅니다. 알 수 없는 정점을 가리키는 엣지는 확정 단계에서 조용히 제외됩니다.
