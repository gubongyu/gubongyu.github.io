## 문제: 백본을 바꾸면 무엇이 함께 바뀌는가

여러 사진을 하나의 3D 좌표계로 모으는 단계에는 카메라와 점군을 추정하는 3D 백본이 필요합니다. met·a·round의 AI 서버는 처음에 VGGT를 사용했고, 이후 MASt3R를 백본으로 쓰는 전략을 추가했습니다.

모델 하나를 교체하는 일처럼 보이지만, 서버 안에서는 모델을 어디서 실행하는지, GPU 메모리를 누가 소유하는지, 좌표의 단위가 무엇인지가 함께 달라집니다. 이 글은 두 전략의 **실행 구조**를 비교합니다.

**2026년 7월 21일의 이식 계획 문서**와 실행 흐름 문서, 현재 저장소의 코드를 바탕으로 정리했습니다. 미리 밝혀 두면, 같은 입력과 조건으로 두 전략의 정확도나 속도를 비교한 평가 자료는 이 저장소에 없습니다. 이 글에서도 그런 비교를 하지 않습니다.

## 조건: 8GB GPU와 하나의 서버 프로세스

개발 환경의 GPU 메모리는 8GB였습니다. 서버 프로세스에는 단일 뷰 검출에 쓰는 모델이 상주하고, 3D 백본은 요청이 들어올 때 실행됩니다. 둘이 동시에 메모리를 차지하면 한도를 넘을 수 있다는 것이 설계 전반의 제약이었습니다.

비교 대상은 두 전략입니다.

- `hybrid_consensus`: 뷰마다 코너를 검출하고 VGGT의 3D 좌표계에서 뷰 간 합의로 병합한다.
- `hybrid_mastr`: 같은 파이프라인에서 3D 백본만 MASt3R로 바꾼다.

저장소에는 검출 없이 평면 교점으로 코너를 구하는 `vggt` 전략도 있지만, 파이프라인 자체가 달라 이 글의 비교에서는 제외합니다.

## 가설: 백본의 출력 형식만 맞추면 나머지는 그대로 쓴다

합의 단계는 순수 기하 계산입니다. 백본이 무엇이든 다음 네 가지만 같은 형식으로 받으면 됩니다.

| 키             | 내용                                  |
| -------------- | ------------------------------------- |
| `world_points` | 뷰별 조밀 점군 (공통 좌표계)          |
| `conf`         | 점군의 신뢰도                         |
| `extr`         | 카메라 외부 파라미터 (cam-from-world) |
| `intr`         | 카메라 내부 파라미터                  |

그래서 백본 실행을 `_run_backbone`이라는 메서드 하나로 분리하고, MASt3R 전략은 이 메서드와 메타 확장 훅(`_augment_meta`)만 교체하도록 구성했습니다. 뷰별 검출, 바닥 평면 적합, 3D로 올리기, 합의, 엣지 구성은 부모 클래스의 것을 그대로 사용합니다.

## 방법: 두 백본의 실행 방식

구조상 차이는 다음과 같습니다.

| 항목            | `hybrid_consensus` (VGGT)                   | `hybrid_mastr` (MASt3R)                                  |
| --------------- | ------------------------------------------- | -------------------------------------------------------- |
| 실행 위치       | 서버 프로세스 안                            | 별도 프로세스(worker)                                    |
| 추론 방식       | 전체 뷰를 한 번의 forward로 처리            | 뷰 쌍별 매칭 후 전역 정렬, 쌍의 수는 뷰 수의 제곱에 비례 |
| 데이터 전달     | 임시 PNG 경로를 넘기고 결과를 메모리로 받음 | 임시 PNG를 넘기고 결과를 npz 파일로 받음                 |
| GPU 메모리 소유 | 서버 프로세스, forward 후 즉시 해제         | worker 프로세스, 종료 시 해제                            |
| 형식 변환       | 필요 없음                                   | 어댑터가 공통 형식으로 변환                              |
| 가중치          | 실행 시 허브에서 자동 로드                  | 로컬 체크포인트 디렉터리 필요                            |
| 좌표 단위       | 문서상 상대 스케일                          | 문서상 미터                                              |
| 메타 확장       | 없음                                        | `metric` 블록, 가능하면 천장 높이                        |

좌표 단위는 저장소 안에서도 표기가 엇갈립니다. 실행 흐름 문서는 VGGT 경로를 상대 스케일로 적지만, 일부 코드 주석은 같은 좌표를 'metric'이라고 부릅니다. 이 글은 실행 흐름 문서의 구분을 따랐고, VGGT 좌표의 절대 스케일을 검증한 자료는 저장소에 없습니다.

### VGGT: 프로세스 안에서 메모리를 비워 가며 실행

VGGT는 서버 프로세스 안에서 실행합니다. 8GB 안에 넣기 위해 여러 조치가 함께 들어가 있습니다. forward 동안 상주 중인 검출 모델을 CPU로 내렸다가 끝나면 되돌리고, 이 파이프라인이 쓰지 않는 출력 헤드를 제거하며, 점군 헤드는 뷰를 하나씩 나눠 처리하게 하고, 결과를 얻은 직후 모델을 해제합니다.

### MASt3R: 프로세스를 분리해 실행

MASt3R를 별도 프로세스로 분리한 직접적인 이유는 메모리가 아니라 패키지 이름입니다. MASt3R가 의존하는 코드가 `models`라는 최상위 패키지 이름을 쓰는데, 서버도 같은 이름을 사용합니다. 한 프로세스에서 함께 불러올 수 없어 worker 스크립트를 따로 띄웁니다.

분리의 결과로 메모리 소유도 달라집니다. worker가 GPU를 쓰다가 종료하면 메모리가 반환됩니다. 다만 서버 프로세스에서 재는 메모리 통계에는 worker의 사용량이 잡히지 않습니다.

worker의 출력은 합의 단계가 기대하는 형식과 달라서 어댑터가 변환합니다. 카메라 행렬을 역변환하고, 뷰마다 격자 크기가 다르면 가장 작은 공통 크기로 맞춥니다. 이때 보간으로 값을 만들어내지 않도록 최근접 방식으로 줄이기만 하고, 내부 파라미터도 같은 비율로 조정합니다.

## 관찰: 문서와 로그에 남아 있는 것

**문서에 기록된 스모크 실행.** 이식 계획 문서에는 room1 실사진 4장으로 두 경로를 끝까지 실행한 결과가 적혀 있습니다. VGGT 백본 경로(매칭 기반 가지치기를 켠 설정)에서 정점 18개·엣지 22개, MASt3R 백본 경로에서 정점 26개·엣지 32개가 나왔고, MASt3R 경로의 메타에는 천장 높이 2.245m가 기록되었습니다. 이 실행의 목적은 완주 여부와 출력 형식의 검증이었습니다. 정답과 대조한 평가가 아니므로, 정점 수의 차이를 어느 쪽이 더 정확하다는 근거로 읽을 수 없습니다.

**서버 로그.** 추론마다 소요 시간이 한 줄씩 기록됩니다. 7월 17일부터 27일 사이의 로그에서 사진 4장 요청을 보면, 직후에 예외가 기록되지 않은 항목 기준으로 `HybridConsensus`는 약 61~165초, `MastrHybrid`는 약 101~113초(3건) 범위입니다. 그러나 이 로그에는 어떤 사진이 입력되었는지가 남아 있지 않고, 기간 중 코드도 계속 바뀌었습니다. 두 전략의 속도를 비교하는 근거로 쓸 수 없는 기록입니다.

**테스트.** MASt3R 경로의 단위 테스트는 worker 출력을 가짜 값으로 대체해 GPU 없이 실행됩니다. 어댑터의 행렬 역변환과 격자 통일, 출력 형식의 준수, VGGT 실행 함수가 호출되지 않는다는 점을 기댓값으로 둡니다.

**인용된 정확도 수치.** 저장소 문서에는 별도 연구 저장소에서 얻었다는 정확도 수치가 인용되어 있고, 두 백본의 코너 출력이 같았다는 설명이 있습니다. 그 평가 산출물은 이 저장소에 포함되어 있지 않아, 이 글에서는 비교 수치로 사용하지 않습니다.

## 한계

- 같은 입력으로 두 전략의 정확도, 소요 시간, 메모리 사용을 비교한 측정이 없습니다. 이 글의 비교는 코드와 문서에서 읽을 수 있는 구조에 한정됩니다.
- 로그의 GPU 메모리 값은 기록 시점의 점유량이며 최대치가 아닙니다. worker의 사용량은 포함되지 않습니다.
- MASt3R 경로는 요청마다 프로세스를 띄우고 모델을 불러옵니다. 쌍의 수가 뷰 수의 제곱에 비례해 늘어나므로 사진이 많아질수록 비용이 커지는 구조입니다. 실제 증가 폭은 측정하지 않았습니다.
- 문서는 MASt3R 경로의 미터 좌표에 초점 거리 편향이 있어 절대값의 오차가 ±20% 수준일 수 있다고 적고 있으며, 줄자로 잰 정답과의 대조는 아직 이루어지지 않은 것으로 기록되어 있습니다.
- 프로세스 분리는 패키지 충돌을 피하기 위한 선택입니다. 파일을 거치는 데이터 전달과 프로세스 기동 비용이 따라옵니다.
